# Clair3 / ClairS — gotchas for ONT germline + somatic SNV calling on the cohort

## Clair3 (germline + WhatsHap/LongPhase phasing)

- **`--use_whatshap_for_final_output_phasing` defaults to True; it CANNOT be cleanly disabled via the CLI**. Confirmed 2026-05-05 on Clair3 v2.0.1 GPU SIF (`/data1/greenbab/software/images/clair3_v2.0.1_gpu.sif`). The flag uses `argparse nargs='?'` with `default=True`. Adding `--use_longphase_for_final_output_phasing` does NOT override whatshap; both end up `True` in the run config and Clair3 silently picks whatshap (`[INFO] 3/7 Phase VCF file using Whatshap`). Passing `--use_whatshap_for_final_output_phasing False` ALSO leaves it `True` — the string `"False"` is truthy. **Workaround**: bypass Clair3's final-output phasing entirely and run `/opt/bin/longphase phase -s merge_output.vcf.gz -b tumor.bam -r ref.fa --ont -o out_prefix` directly on Clair3's unphased `merge_output.vcf.gz`. The `longphase` binary is bundled in the same Clair3 SIF.

- **Whatshap vs Longphase — pick whatshap for per-read haplotag use cases** (integration assignment, allele-specific methylation). Empirical A/B on chr20 + 20% subsample of p17424_1 tumor BAM (2026-05-05): whatshap phased 96.0% of HET sites with 131 blocks (largest 7,022 vars / 358 kb); longphase phased 76.4% with 198 blocks (largest 8,417 vars / 680 kb). Longphase produces fewer/larger blocks — better long-range contiguity but ~24% of HETs go unphased. For tagging chimeric reads at integration junctions, the higher phase rate from whatshap matters more than block extent. Wall-clock difference at chr20-20%: whatshap ~133 s, longphase ~10–13 s — the phaser is not the bottleneck (Clair3 GPU SNV calling is); don't pick longphase just for speed.

- **Clair3 emits `PS` in genotype FORMAT but omits the `##FORMAT=<ID=PS,...>` declaration from the VCF header**. Confirmed v2.0.1: data rows show `GT:GQ:DP:AD:AF:PS  0|1:7:5:4,1:0.2:60591` correctly, but the header has no `##FORMAT=<ID=PS,...>` line. Strict VCF parsers (some Python libraries, some bcftools downstream tools) may warn or refuse. **Fix**: `bcftools annotate --header-lines <(echo '##FORMAT=<ID=PS,Number=1,Type=Integer,Description="Phase set identifier">') in.vcf.gz -Oz -o fixed.vcf.gz && bcftools index -t fixed.vcf.gz`. The data is functionally valid; only the header line is missing.

- **Verifying phasing actually ran**: a Clair3 run with `--enable_phasing` may produce both `merge_output.vcf.gz` (unphased) and `phased_merge_output.vcf.gz` (phased). Check by counting genotypes that contain `|`: `zcat phased_merge_output.vcf.gz | grep -v '^#' | awk -F'\t' '$10~/^[01]\|[01]/' | wc -l`. Don't grep for `##FORMAT=<ID=PS` in the header — see above.

- **Model match for ONT 5kHz dorado sup data**: Clair3 v2.0.1 SIF bundles the right model at `/opt/models/r1041_e82_400bps_sup_v500`. The dorado v500 series matches data basecalled with `dorado VN:1.0.1` using `sup,5mCG_5hmCG@latest,6mA@latest`. Verify the basecaller from the BAM `@PG` line (`samtools view -H tumor.bam | grep -i 'PG.*dorado'`) before picking the model. Mismatched models silently produce noisy HET calls that break downstream phasing.

- **Resource sizing — full-WGS ONT 30× tumor with `--enable_phasing` + WhatsHap haplotagging on Clair3 v2.0.1 GPU**: chr20-20% (~119k reads, ~6× cov) finished in 4:12 wall on H100 80GB. Full-WGS scaling is non-linear (Clair3 chunks per-contig and parallelises on GPU); allow 4–6 h wall budget per BAM with 8 cpu / 64 G / 1 GPU. The phasing step itself adds ~1–2 min on a chr20 subset, more on full WGS but still small relative to SNV calling.

## ClairS (paired tumor/normal somatic)

- **`/opt/models` is empty in `/data1/greenbab/software/images/clairs_latest.sif`**. Confirmed 2026-05-05 on v0.4.5 SIF — the bundled `/opt/models/` directory is empty (the build doesn't ship pretrained models). At runtime, ClairS searches `$HOME/miniforge3/bin/clairs_models/<platform>/pileup.pkl` (apptainer inherits HOME). **Fix**: download the official tarball once to a shared location and pass model paths explicitly. `wget http://www.bio8.cs.hku.hk/clairs/models/clairs_models.tar.gz` (832 MB, last-modified Nov 18 2025). Extract to `/data1/greenbab/users/ahunos/apps/clairs_models/`. Pass per-run: `-P <models>/<platform>/pileup.pkl -F <models>/<platform>/full_alignment.pkl --indel_pileup_model_path <models>/<platform>/indel/pileup.pkl --indel_full_alignment_model_path <models>/<platform>/indel/full_alignment.pkl --clair3_model_path <models>/clair3_models/r1041_e82_400bps_sup_v420`. Tarball includes all platforms in one extraction.

- **`_ss` vs `_ssrs` model variants — the tradeoff is documented but cancer-type guidance is not**. From the ClairS README: `ssrs` is "trained initially with synthetic samples and then real samples augmented" (recommended default per maintainer @zhengzhenxian, GitHub issue #53). `ss` is "trained from synthetic samples" only — README explicitly says "ss model can be used when missing a cancer-type in model training is a concern." Real-sample training for v0.4.0 ssrs was HCC1937, HCC1954 (breast), H1437, H2009 (lung) — i.e. solid tumors. **For hematologic cancers (ATLL etc.), no maintainer guidance exists**; default to ssrs but consider running both as a sensitivity check. Empirical A/B on chr20-20% T/N pair (p17424_1, 2026-05-05): ss is 2.6× more permissive than ssrs (980 PASS SNV vs 370 PASS SNV); ssrs callset is nearly a strict subset of ss (10 ssrs-only records, 2,856 ss-only, 1,122 in both).

- **ClairS internal Clair3 model is v420, NOT v500** — even though the standalone Clair3 v2.0.1 SIF bundles v500. The `clairs_models.tar.gz` tarball ships `clair3_models/r1041_e82_400bps_sup_v420/`. Author endorses `_ssrs` for nearby cross-version use (v4.x basecallers; GitHub issue #53), but **dorado v500 is not explicitly addressed by maintainer**. Empirical preflight (2026-05-05) showed internal germline HET selection healthy on v500-basecalled data: `Total HET SNP calls selected: chr20: 80936, ... pro: 0.9935`. So the v500/v420 mismatch isn't catastrophic at the germline-calling step. Still flag this in Methods for any manuscript citing ClairS calls.

- **`--haplotagged_tumor_bam_provided_so_skip_intermediate_phasing_and_haplotagging` reuses Clair3's prior phased+haplotagged BAM**. Documented since v0.3.1 (2025-08). When chaining Clair3-phasing → ClairS, this flag avoids the redundant whatshap step inside ClairS. Saves ~30 min compute per ClairS run on full WGS. Cost: introduces a sequential dependency (Clair3 phasing must finish before ClairS starts). For cohort runs with abundant GPU parallelism, prefer the no-dependency path (let each ClairS run do its own internal phasing) — wall-clock wins, atomic-retry is simpler.

- **`--enable_indel_calling` is OFF by default**. Adding it adds ~30% to wall time but produces a `indel.vcf.gz` somatic indel output alongside `output.vcf.gz` (somatic SNV). For ATLL where driver indels exist (e.g. CCR4, TBL1XR1), this flag is mandatory.

- **Resource sizing — ClairS T/N + indels on chr20-20%**: 26:45 wall (both ssrs and ss back-to-back), peak 13 GB RSS, on a single H100 80GB. Project full-WGS to 6–8 h per ClairS run with 8 cpu / 64 G / 1 GPU. Cohort of 6 patients × 2 model variants = 12 ClairS jobs.

- **GitHub issue #53 is the authoritative maintainer thread on basecaller-version compatibility**. Quote (Zhengxian Zheng, ClairS author, in response to a v4.3.0 question): "We have a new model fine-tuned on real samples, pls kindly try the `-p ont_r10_dorado_sup_5khz_ssrs` for your basecalled data." A follow-up question about v5.2.0 in the same thread is unanswered as of Nov 2025. The principle from issue #52 (R9 thread, same maintainer): pick the model whose training basecaller's *architecture* most closely resembles yours. v420 ↔ v500 is closer than R9 ↔ R10 by that standard.

## ClairS contaminated-matched-normal caveat

- **For matched-N BAMs with tumor-cell contamination, ClairS will undercall somatic SNVs**. ClairS's "subtract germline" logic flags variants present in both tumor and normal as germline. If the normal is contaminated (e.g. NK-sort fraction containing HTLV-1+ tumor cells in our cohort: p17424_3 normal at 43.3× HTLV-1, p17424_6 at 2.5×), genuine somatic mutations also appear at low VAF in the normal and are filtered out. Three options when this happens: (a) accept undercalling and document in Methods; (b) re-run those patients with **ClairS-TO** (tumor-only, separate SIF `hkubal/clairs-to`); (c) use a panel-of-normals from clean cohort samples. For the May 2026 ATLL cohort run, option (a) is the default — flag p17424_3 and p17424_6 in the output table for downstream interpretation.
