- **"No rule to produce" for valid targets**: Check for whitespace in sample names or paths in the sample sheet. As a workaround, extract the failing step into a standalone shell script.
- **Double-container invocation**: If a rule sets the `singularity:` directive, do NOT also add `singularity exec -B` inside the `shell:` block. The directive handles container execution automatically.
- **Config access**: When using `--configfile`, values are accessed as `config["key"]`, not `config.key`.
- **Cluster profile conflicts**: When using `--workflow-profile` with SLURM, ensure resource keys (`mem_mb`, `threads`, `runtime`) do not conflict with the cluster profile's own defaults. Check `.snakemake/log/` for the actual submitted job command if jobs fail silently.
- **`--profile` absolute path required when `--directory` is set**: Snakemake resolves `--profile` relative to `--directory`, not relative to `--snakefile`. When the pipeline lives in one directory and the experiment in another, always pass `--profile` as an absolute path.
- **Snakemake 9 `srun` memory conflict** (`SLURM_MEM_PER_NODE` vs `SLURM_MEM_PER_CPU` fatal): `snakemake-executor-plugin-slurm` wraps each rule's shell in `srun` inside the `sbatch` job. Snakemake 9 also injects a built-in `mem_mb = 1000` default. Fix: use `mem_mb_per_cpu` (not `mem_mb`) in all rule `resources:` blocks, and add `mem_mb: 0` to profile `default-resources` to zero out the built-in default. **ADDITIONAL**: If the Snakemake coordinator itself is submitted as an sbatch job (e.g. via submit_snakemake.sh), use `#SBATCH --mem-per-cpu=XXXX` (never `--mem=XG`) for the coordinator — `--mem` sets `SLURM_MEM_PER_NODE` in the coordinator env which propagates via `--export=ALL` to rule jobs, creating the same conflict. Also add `unset SLURM_MEM_PER_NODE` at the top of the coordinator script. Confirmed fix: 2026-02-26.
- **Missing SLURM account causes silent rejection**: Add `slurm_account: <account>` to profile `default-resources`. The executor plugin does not read `SLURM_DEFAULT_ACCOUNT` from the environment.
- **`software-deployment-method: apptainer` breaks conda-based pipelines**: Setting this wraps every rule's shell command in `apptainer exec`, breaking all rules that do not have a container directive. Omit it entirely for conda-based pipelines (see GPU note in §6 for when to use it).
- **Stale lock file after killed coordinator**: Run `snakemake --unlock` before resubmitting. Add `--rerun-incomplete` on resubmission to pick up partial outputs.
- **Rerun control — three knobs for when default re-runs are too aggressive**: Snakemake 7+ invalidates outputs on ANY change to {`mtime`, `code`, `params`, `input`, `software-env`}. Editing downstream rules touches the workflow hash and re-triggers UPSTREAM rules whose shell is byte-identical (cost: ~24–48 h to re-basecall a single ONT sample on `componc_gpu`). Three tools, in order of safety:
    - `--rerun-triggers mtime` — fall back to Make-style "input newer than output". Use when the upstream-rule diff is cosmetic (renaming a downstream output, adding a new sibling rule, refactoring whitespace). Confirmed 2026-04-25 on the ATLL dorado sandbox after appending a `samtools_sort_index` rule — basecaller + aligner correctly skipped, only the new rule executed.
    - `--cleanup-metadata <output>` — wipe provenance for one specific output. Surgical alternative when you only need to skip one rule's rerun rather than disabling triggers globally.
    - `--touch` — mark outputs as up-to-date without running. DANGEROUS — only when you've manually verified the file content is correct.
  None of these should mask a real logic change; outputs become stale. Always eyeball the diff first.
- **PATH lookup is not dependable inside rule jobs — every executable a rule needs must be an ABSOLUTE path.** The SLURM executor nests two levels: the coordinator `sbatch`es a job whose `--wrap` runs `snakemake --mode remote`, and that inner Snakemake `srun`s the rule's shell. Environment set on the coordinator does not reliably reach the innermost level even though the plugin submits with `--export=ALL`. Confirmed 2026-09-02/04 on the DSS DMR pipeline, where **one root cause surfaced four times in a row**, each as a different missing binary, each costing a full coordinator cycle:
    - `conda` — rules with a `conda:` directive died with `/usr/bin/bash: conda: command not found` / `WorkflowError: Error running conda info` (exit 127). See the dedicated bullet below.
    - `python3` in a rule shell — resolved to RHEL 8's `/usr/bin/python3` (3.6), giving `SyntaxError: future feature annotations is not defined` (needs ≥3.7) in one rule and `ModuleNotFoundError: No module named 'pandas'` in another. Note 3.6 is old enough that the failure looks like a code bug, not an environment bug.
    - `apptainer` in a called shell script (`COMBP="apptainer exec ..."`) — `apptainer: command not found`, the same failure already documented in the `analysis-gotchas` skill → `references/severus.md`.
    - `apptainer` again, one rule downstream, inside a Python script building `["apptainer", "exec", ...]` for `subprocess`.
  **Fix pattern**: register every binary in the workflow config (`tools.apptainer`, `tools.python_env`, …) and pass it into scripts as an explicit argument with a PATH fallback for hand runs, e.g. `APPTAINER_BIN="${APPTAINER_BIN:-${4:-apptainer}}"` plus an up-front `command -v` check that fails loudly instead of dying mid-pipeline. **When one of these surfaces, immediately `grep` every script the rules invoke for bare `apptainer`/`python3`/`Rscript` rather than fixing them one failed run at a time** — each cycle here cost 18–40 min of wall clock, and two of the four were avoidable by sweeping after the first.
- **Snakemake's `conda:` deployment can be unusable on a cluster where `conda` is only a shell function.** `conda` is defined by `conda.sh` as a shell FUNCTION, not a binary; functions do not survive into the non-interactive `/usr/bin/bash -c` that Snakemake uses to run `conda info --json`. Two fixes that look right and are **not sufficient**, both confirmed failing 2026-09-04: (a) `conda-base-path: /home/<user>/miniforge3` in the profile — the flag verifiably reached the remote job's argv and it still failed; (b) `export PATH=/home/<user>/miniforge3/condabin:$PATH` in the coordinator — a direct child shell of the coordinator then resolved `condabin/conda` correctly, but the PATH did not survive `sbatch` → `srun` to the innermost step. **Working approach**: skip the deployment mechanism entirely. Build the env once at a stable prefix (`mamba env create -p <repo>/envs/<name> -f envs/python.yaml`), register the prefix in config, and call `<prefix>/bin/python3` directly with `PYTHONNOUSERSITE=1`. Keeps the version pinning and the protection against `~/.local` shadowing, drops the fragile machinery. Keep the `environment.yaml` as the version manifest and build input.
- **`~/.local/lib/python3.X/site-packages` silently shadows a conda env.** Audit before trusting any "pinned" Python env: `python -c "import pandas; print(pandas.__file__)"`. On the DSS project 2026-09-02 the active `snakemake` env imported `pandas` from user-site while `conda list` recorded a different provenance, and imported versions disagreed with recorded dist metadata (numpy 2.2.6 recorded vs 2.4.3 imported; matplotlib 3.10.3 vs 3.10.8). None of that is visible in an environment export, and it changes under any `pip install --user`. Always set `PYTHONNOUSERSITE=1` in rule shells, and pin to what actually **imports**, not to what `conda list` claims.
- **Validate an environment fix on ONE target before resubmitting the whole coordinator.** `snakemake <absolute/target/path> --configfile ... --profile ... --jobs 1` runs a single rule through the real submission path in ~2 min and reproduces cluster-only failures that a login-node dry-run cannot. Two gotchas when doing this: put the target **before** the flags (a target placed after `--rerun-triggers` is consumed as that flag's value), and do **not** use `--` as a separator — with a profile in play it makes the profile's `set-resources` entries parse as targets (`MissingRuleException: No rule to produce run_dss_dmr:runtime=480`).
- **A dry-run on the login node validates the DAG, not the runtime environment.** `snakemake -n` passed cleanly before every one of the four failures above, because all of them are compute-node PATH problems. Treat a green dry-run as evidence about wildcards, inputs and rule wiring only.
- **Never run two Snakemake coordinators in the same `--directory` at once, even with disjoint outputs and different configs.** They share `.snakemake/` state. Confirmed 2026-09-25 (mouseLINE1 S10 rescan, v3 and v4 configs launched together): a rule job died at startup in `persistence.drop_iocache()` with `FileNotFoundError: .snakemake/iocache/latest.pkl` because the other instance had just removed it. The failure looks like a random rule error, and the rule's own log is stale (the job died before writing it). Run the configs one after the other, or give each its own `--directory`.
- **A "Software environment definition has changed" rerun reason can pull in unrelated upstream rules** (seen for a container rule whose SIF path was unchanged). When only new rules are being added, `--rerun-triggers code params input` keeps the DAG to what actually changed. But then a change *inside* a script input is not a trigger, so delete (or `--forcerun`) the outputs of rules whose script you edited.

## snakemake-executor-plugin-slurm 0.5.x: `slurm_account` makes every submission call `sacctmgr` (added 2026-09-26, RetroEM Problem B)
- With `slurm_account` set (profile `default-resources` or rule), the plugin runs `sacctmgr -n -s list user $USER` before **each** `sbatch`. One refused slurmdbd connection (`_open_persist_conn ... Connection refused`, seen twice on iris in one evening) raises `WorkflowError`, and the coordinator exits and **cancels every running job** (long arm runs lost; the log then lists them as "Error in rule ... CANCELLED", which are not real rule failures).
- Fix: leave `slurm_account` unset and pass the account through `slurm_extra`, e.g. `--default-resources slurm_partition=cpushort "slurm_extra='-A <account> --exclude=isca071'" mem_mb=0 mem_mb_per_cpu=4000 runtime=60`, where `<account>` is `slurm_account` in `$SITE_CONFIG/executor.yaml`. Without `slurm_account` the plugin guesses once via `sacct` and only warns on failure. (The note above about silent rejection without an account still holds: the account must reach sbatch, here via `-A`.)
- After such a crash, move unfinished run directories aside before relaunching if the rule's script does not clear its output directory (stale partial chunks can be picked up).
- **A SLURM-executor coordinator can hang silently: its log stops, its child job has finished, and it sits at 0 CPU.** Seen 2026-09-27 (mouseLINE1 v4, job 15187859). A child finished at 00:35, the coordinator never logged it, and 40 min later it was still RUNNING with no CPU used over a 60 s sstat window. This came hours after slurmctld had throttled RPCs (`scancel: _add_delay: adding delay in RPC send`). Detect it: poll the coordinator log's mtime and alert when it is unchanged for > 20-25 min while `squeue` shows no child jobs, then confirm with `sstat -j <id>.batch -o AveCPU` twice, a minute apart. Recover: `scancel` the coordinator, `snakemake --unlock`, resubmit the same targets. Completed outputs are kept, and `--rerun-incomplete` redoes any job left half-registered.
