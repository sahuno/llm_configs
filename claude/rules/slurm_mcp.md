- **`mcp__slurm__slurm_submit_batch` injects fixed defaults on the sbatch cmdline** that override `#SBATCH` directives in the script: `--account greenbab`, `--nodes 1`, `--ntasks-per-node 1`, `--cpus-per-task 8` (default), `--mem 64G` (default), `--time 04:00:00` (default), `--output /home/ahunos/slurm_logs/<jobname>_%j.out` (default), `--error` analogous. To override, pass them explicitly to the mcp tool (`cpus`, `mem`, `time`, `partition`, `job_prefix`).
- **Fatal `--mem` vs `--mem-per-cpu` conflict**: if the script has `#SBATCH --mem-per-cpu=4G` and mcp adds `--mem 64G` on cmdline, sbatch refuses with `--mem, --mem-per-cpu, and --mem-per-gpu are mutually exclusive`. Fix: remove `--mem-per-cpu` from the script and pass `mem` explicitly to the mcp tool, OR submit via direct `sbatch` for full control.
- **`--exclusive` is NOT exposed by mcp's submit_batch** but `#SBATCH --exclusive` in the script *is* honoured (mcp doesn't override what it doesn't set). Same for `#SBATCH --exclude=<nodelist>`.
- **`--array` is not supported by mcp's submit_batch.** mcp's job-id parsing assumes one job per submission. For SLURM array jobs, use direct `sbatch script.sbatch` via Bash. mcp's `slurm_job_status` and `slurm_job_logs` will accept the array-job IDs after submission.
- **mcp redirects logs to `/home/ahunos/slurm_logs/`** regardless of `#SBATCH --output` in the script. Read logs from there, not from the path you set.
- **For batches > ~20 jobs, prefer a Python driver** that calls `subprocess.run(["sbatch", script])` directly. Faster (no per-call mcp round-trip), gives full sbatch control, and works with arrays. Use mcp tools for *monitoring* (`slurm_job_status`, `slurm_job_logs`, `slurm_queue_info`) where they shine.
- **Account is auto-injected** by mcp; for direct sbatch you may need `#SBATCH --account=greenbab` explicitly (the executor plugin and direct sbatch don't always read SLURM_DEFAULT_ACCOUNT — see also `rules/snakemake.md`).
- **`SLURM_JOB_NAME` suffix as a parameter channel for parallel mcp submissions**: `mcp__slurm__slurm_submit_batch` doesn't expose `--export`, so identical wrapper scripts can't be parameterized via env vars at submission time. Trick that works: pass K copies of the same wrapper to `submit_batch` with one `job_prefix`. mcp auto-suffixes `_01.._NN` to the job name. Inside the wrapper, parse the trailing index off `${SLURM_JOB_NAME}` (`grep -oE '[0-9]+$'`) and derive whatever per-replicate parameter you need (e.g., `PERM_SEED=$((1000 + index))`). Confirmed 2026-04-29 with K=10 permutation FDR submissions — all 10 picked up unique seeds without per-perm wrapper files. Cleaner than generating N hardcoded sbatch scripts.
- **Headroom can be deceptive — always check `slurm_queue_info` before assuming saturation**: 10 × 24-cpu / 384G jobs were submitted to componc_cpu on 2026-04-29 21:43 and all 10 entered RUNNING within 10 seconds across 10 different nodes (isca014/16/17/18/23/25/39/150/151/152). Despite project lore that componc_cpu is usually saturated (and `rules/mskcc_partitions.md`'s general guidance to prefer cpushort), capacity fluctuates. For batches < ~12 jobs at moderate request size, a `slurm_queue_info partition=componc_cpu` check before submission reveals when the partition is actually idle and worth using.
